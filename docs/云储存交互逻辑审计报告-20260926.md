## 1. 当前拓扑

```
[浏览器 localStorage]                    [Supabase ysp_state]
  ysp_data  ← 业务数据 + _rev + snapshots    id=stateId（单行，PATCH 整包覆盖）
  ysp_ui    ← 云配置 / 会话 / cloudRev 基线
              + operationLogs（≤500）
                     │ 800ms 防抖 / 30s 周期 / 启动 / 手动 / 关闭 keepalive
                     └──────────▶  upload（整包 payload）
                     ◀───────────  分歧时逐槽位弹窗
```

云端为**单行整包覆盖，无服务端版本历史，无乐观并发控制**：`cloudStore.js:245-257` 的 PATCH 不带 `If-Match`，也不带 `updated_at` 前置条件，服务端层面是 **last-writer-wins**。

客户端靠两条机制在**下一次同步时**检测分歧：

| 机制 | 位置 | 作用 |
|---|---|---|
| 槽位版本号 `_rev`（9 槽位） | `cloudSlotPlan.js:56-59` | payload 内随数据上传 |
| 同步基线 `cloudRev` | `store.js:45`（随 `ysp_ui` 持久化） | 设备侧记住"上次同步看到的版本" |
| `computeSlotPlan` | `cloudSlotPlan.js:74-91` | 三方比对：本地 rev / 基线 / 云端 rev → `align` / `upload` / `adopt-cloud` / `conflict` |

`computeSlotPlan` 判定顺序：

1. 内容一致短路 → `align`
2. 本地与云端都相对基线移动 → `conflict`（弹窗）
3. 仅云端移动 → `adopt-cloud`（静默采纳）
4. 仅本地移动 → `upload`（静默上传）
5. 都未移动但内容不同 → `conflict`

### 已生效的保护

| 保护 | 位置 |
|---|---|
| 9 槽位独立版本，分歧只影响相关槽位 | `cloudSlotPlan.js:1-5` |
| 内容一致短路，防止误弹窗 | `cloudSlotPlan.js:79` |
| 逐槽位损坏守卫（云端缺槽 / 错型 → 回退本地） | `store.js:421-429` |
| 8 集合应用前守卫（拒绝应用空数组覆盖非空本地） | `App.vue:520-532` |
| 强警告二次确认（选云端前查数量骤减 / 销售日期倒挂） | `App.vue:352-371`、`dataProtection.js:41-65` |
| 重入锁，同一页不并发同步 | `store.js:338` |
| 关闭前 keepalive 保底上传 | `App.vue:908-935` |
| 云端未连接时本地未同步改动清单 | `store.js:1075-1083` |

## 2. 误操作 / 数据丢失风险

| # | 风险 | 触发路径 | 严重度 |
|---|---|---|---|
| **L1** | **陈旧回写静默覆盖** | 设备 B 在设备 A 上传之后、B 自己编辑之前读取了云端；B 随后编辑无关槽位 Y → B 整包上传，携带 **X 的旧内容与旧 rev（rev 回退）**。A 下次同步：A 基线已是 2、本地 rev 2 = 基线 → 判定 `adopt-cloud`，**静默采纳 B 的陈旧 X，A 自己的修改永久丢失，无任何提示** | **高** |
| **L2** | **租约"只读"是假只读** | `tabLease.js` 仅设置 `otherTabEditing` 渲染横幅，**无任何写入拦截**（`saveToLocalStorage` 不检查它）。横幅文案"本页已锁定为只读"与实际行为不符 | **高** |
| **L3** | **JSON 导入零防护** | `App.vue:757` `handleImport` 直接 `loadData(json)` + 保存，**无 `confirm()`、无导入前备份**。一步操作可整体摧毁数据，且 `app_import` 是回放 BARRIER | **高** |
| **L4** | 静默采纳不可撤销 | `performSyncDecision` 传 `trackHistory: force`；仅手动同步 `force=true`。防抖 / 周期 / 启动的自动采纳走 `setHistorySuppressed(true)` → 不压栈，无法撤销 | 中高 |
| **L5** | 多 tab 覆盖写 | `storage` 事件与租约**都只弹横幅、不阻塞**；后写者覆盖整个 `ysp_data`，先写者的内存态若在关闭前未同步即丢失 | 中 |
| **L6** | 撤销历史易失 | `undoStack` 上限 20（`MAX_UNDO_STEPS`），且**不持久化**（`saveUiStateToLocalStorage` 不含它）→ 刷新即全丢 | 中 |
| **L7** | 基线丢失方向 | 清除 localStorage / 换设备 → `cloudRev = {}` → base=0，本地与云端均判"已移动" → 落入 `conflict` **弹窗**（安全方向，不误覆盖） | 低（已自愈） |
| **L8** | 分歧可能长期悬挂 | `cancelSlotConflict` → 整轮跳过；`silent` 模式遇分歧也整轮跳过并只记日志，不阻断也不解决 | 低 |
| **L9** | 备份依赖浏览器下载 | `downloadJsonBackup` 由程序触发，浏览器可能静默拦截；且仅在页面可见时触发 | 低 |

### L1 详解（真正的设计缺口）

rev 模型隐含假设"rev 单调递增"，但并发写入会让云端收到**更低的 rev**，而该情况被解释为"只有云端动了"→ 静默采纳。

```
时间线（两台设备，共用同一 stateId）
────────────────────────────────────────────────────────
T0   云端 X.rev = 1
T1   设备 A：编辑 X → X.rev = 2，上传
T1'  云端 X.rev = 2（A 的内容）
T2   设备 B：编辑 Y → Y.rev = 2；B 内存中 X.rev 仍为 1（陈旧）
T3   设备 B：整包上传 → 云端 X.rev = 1、X 内容 = B 的陈旧副本   ← 静默回退
T4   设备 A：下一次同步
       本地 X.rev = 2，基线 = 2 → localMoved = false
       云端 X.rev = 1，基线 = 2 → cloudMoved  = true
       plan[X] = adopt-cloud                                  ← 静默覆盖
T5   设备 A：采纳陈旧 X → A 自己的修改永久丢失，无提示
```

内容一致短路（`cloudSlotPlan.js:79`）救不了，因为两边内容确实不同。

**修复方向**：上传前增加前置校验 —— 若本地某槽 `rev ≤ 云端 rev` 且内容不同，则按 `conflict` 处理，阻断陈旧回写。

## 3. 兜底与逆向回溯能力

| 机制 | 现状 | 能否救数据 |
|---|---|---|
| 每日 JSON 备份 | `maybeAutoBackup`（`store.js:631`）每日首次保存时下载，含操作日志；需页面可见；浏览器可能静默拦截 | ⚠️ 仅 1 份/天，最长 24h 空窗；文件落在用户 Downloads，应用侧无留存 |
| 操作日志 | 上限 **500 条**即永久截断（`store.js:1052`）；存 `ysp_ui`，**不上传云端**（`exportData` 不含日志）→ 单浏览器独有 | ⚠️ 部分；跨设备 / 跨浏览器无效 |
| **`logReplay.reconstructAtTime`** | 纯函数回放引擎已实现且有测试，**但零 UI 引用**（`*.vue` 中无任何引用；文件头自述"仅作验证/研究工具，不接入 UI"） | ❌ **用户当前完全无法使用回溯** |
| undo / redo | 内存态、上限 20、刷新即丢 | ❌ 非持久 |
| `snapshots` | 每日 8 项**聚合指标**（利润 / 库存 / 借贷） | ❌ 不可还原明细 |
| 云端历史 | 无（单行覆盖） | ❌ |

### 回溯引擎的第二个缺口

`logReplay.js:384` 靠正则 `/下载|选择使用云端数据/` 识别云端覆盖 BARRIER，但 C2 改造后引擎日志措辞已改为 `'同步完成'`、`'云端槽位损坏/缺失…'` 等 → **正则不再命中**。

后果：云端覆盖类日志落入 `no_inverse_handler` → 被**静默跳过**，回放跨越一次云端覆盖会产生错误状态却不报错。

更根本的问题：这些 `cloud_sync` 日志**本身不存 `before` 快照**，即使修好屏障也无法逆放。

### 回放能力分级（`logReplay.js:15-56`）

| 分级 | 含义 | 类型数 |
|---|---|---|
| FULL | 日志含完整 before，可精确逆放 | 20 |
| PARTIAL | 记录了变更但缺前置状态，逆放不精确 | 5 |
| BARRIER | 整体状态替换，遇到即中止回放 | 4（`app_import` / `cloud_pull` / `app_undo` / `app_redo`） |
| NOOP | 无业务变更，跳过 | 6 |

## 4. 结论

| 维度 | 结论 |
|---|---|
| 多设备顺序使用 | ✅ 安全。逐槽冲突弹窗 + 内容一致短路 + 逐槽损坏守卫，能挡住绝大多数分歧；基线丢失时降级为"弹窗"而非"覆盖"，方向正确 |
| 并发写入 | ❌ 不安全。L1 是真实的数据丢失路径；L2 / L5 使多 tab 场景缺乏任何强制保护 |
| 能逆向回溯 | ❌ 目前不成立。能力已写好但未接入 UI，且云端覆盖无 `before` 快照、BARRIER 正则已失效 |
| 单浏览器日常使用 | ✅ 基本安全，有二次确认与逐槽守卫兜底 |

**用户关心的"2 个 tab 输入导致丢失数据"—— 结论：会发生，且存在静默丢失路径（L1 / L2 / L5 组合），当前仅靠横幅提示，无强制保护。**

## 5. 建议（按性价比）

| 优先级 | 动作 | 成本 |
|---|---|---|
| **P0** | 导入前加 `confirm()` + 自动生成一份导入前备份（`handleImport`） | 极小，堵住 L3 |
| **P0** | 采纳云端前，把被覆盖槽位记入带 `before` 的日志或自动落一份 JSON | 小，让 L1 / L4 可救 |
| **P1** | 上传前校验：本地某槽 `rev ≤ 云端 rev` 且内容不同 → 按 `conflict` 处理，阻断陈旧回写 | 中，根治 L1 |
| **P1** | 把 `reconstructAtTime` 接一个"回溯到时间点"只读预览 UI；修好 BARRIER 正则 | 中 |
| **P2** | 租约升级为真实写拦截（或至少禁用输入），横幅文案与实际行为对齐 | 中，L2 / L5 |
| **P2** | undoStack 持久化 + 扩容 | 小 |
