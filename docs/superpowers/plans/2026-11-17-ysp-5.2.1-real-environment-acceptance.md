# YSP 5.2.1 真实环境验收手册

适用版本：GitHub Pages 5.2.1，发布提交 `074c347`。本文是一份待执行的验收方案。源文件抽查、历史回归测试和构建结果只作准备依据。每条实际结果应单独登记。

## 1. 准备环境与基准

1. **线上观察组**：机器 A 用日常桌面浏览器，机器 B 用另一台电脑或独立浏览器用户资料，手机用原有移动查询页。线上只观察线上版本、登录前后的读取范围、桌面与移动端展示、现有历史档案和下载打印。开始前确认所有设备没有未同步编辑。发现线上冲突时，先记录双方信息，取消或退出。
2. **写入演练组**：另建仅含合成数据的 Supabase 项目。用 5.2.1 同一提交构建测试站，独立 HTTPS 源，同站下包含主程序和移动页。两台设备访问同一测试站。配置 `stateId=main`、关闭公开读取，仅用测试项目的公开客户端 Key。按 README 创建表、配置基础权限，并应用仓库内的 main 修订号、main 私有化、car 档案三份迁移。后台核对测试行的 `id=main`、所有者、`revision`、`is_public=false`。**仅换主项目中的行名不足以测试 main 专属规则。**
3. **账号**：测试账号 O 是 main 行所有者，A/B 共用 O 进行跨设备测试。账号 X 也是已登录用户，但不拥有 O 的账本。无痕或另一独立资料用作匿名端。同一浏览器资料开两个标签用于测同源编辑锁。Papa/Payton 是账本内的归属，测试时不得代替 O/X 的登录账号矩阵。
4. **备份样本**：第一份是真实文件的本地离线副本，优先使用已核对的 Downloads 中 `PhotonRing数据Manual_20261116.json`。另留修复前文件和 `car_backup_2026-11-13.json` 的原件。真实数据只装载到独立、本地、断开云端的浏览器资料；先确认页面没有生产云配置或登录凭证。第二份是可以上传至演练项目的合成账本。所有演练记录加 `QA-日期-用例号` 前缀。
5. **证据**：固定 Asia/Shanghai 时区，记录 A/B 的时间、浏览器和版本，打印另记 Excel 版本、打印驱动和实际纸盒。每个用例至少记录操作前、操作后两份比对结果。实际记录存到本机私有目录，截图、日志片段和报告遮住账户凭证与个人信息。每个二进制备份记录 SHA-256，例如 `Get-FileHash -Algorithm SHA256 -LiteralPath '文件绝对路径'`。
6. **恢复比较口径**：金额用原数值比较，界面按两位小数对照。商品按内部 `id` 逐条比较，SID 用来查找，不作为唯一键。其他集合按稳定业务键比对，重复记录保留计数。先对比主业务字段，再单列版本、时间戳、同步修订号、按日期合并的快照和本机设置。两次导出的文件哈希不同，不能单凭这一点判定数据损坏。

建议先做登录和恢复，再做并发和跨业务写入，再做提醒、打印、档案。合成账本在各组之间恢复到明确的基准。线上观察可最后进行，避免把演练浏览器资料误当日常使用。

## 2. 多设备并发与账号权限

### SYNC-01 同一浏览器的多标签锁

1. 在测试站 A1 用 O 完成同步。打开同浏览器资料、同一地址的 A2。预期 A2 显示“本页暂时只读”，不得落盘或修改云端。
2. A1 编辑一条测试商品名称并保存。记录 A1 的修改时间和云端修订号。A2 查看是否出现另一标签页更新提示。若界面提供“下载本页副本”，保留副本并标注它仍是旧视图。
3. 关闭 A1，A2 点“重新取得编辑权”。核对它先读到修改后的商品，再编辑另一字段，刷新重开后两项改动都在。
4. 独立重复一次用强制结束 A1 浏览器进程，保留测试数据，随后从 A2 尝试重新取得。记录能否在关闭后恢复编辑，及提示是否准确。

**证据与通过标准**：A1/A2 状态截图、前后商品和修订号。两页不能同时具有编辑权；接管后不得用旧内存状态覆盖新数据。

### SYNC-02 两台设备同一模块冲突、旧时间与取消

1. A/B 用 O 同步到相同修订号 R，分别截取相同测试商品的售价、运费、到账状态及本地业务修改时间。B 断网或关闭应用。
2. A 改售价及运费并同步。确认云端快照已是新值。B 恢复网络，先只打开页面，截取冲突内的“云端／本地”时间和实际业务差异。另跑一次 B 打开约一秒就关闭，之后确认云端业务值和修订号仍是 A 的版本。
3. B 出现提示时先取消，再刷新重开。可同时记录应用显示的本地业务时间和本地账本 `updatedAt`。只打开、查看或取消，不应把旧账本的本地业务修改时间刷新成当前时间，也不应丢失任何一边的业务数据。
4. 从共同基准再跑一次双端都离线修改同一商品。A 改售价并先提交，B 改运费并切为已确认，随后 B 重连。展开全部差异，逐项核对中文字段名、币种、金额、新旧值，及“已确认／未确认”、入账日期。仅预选一边时检查数据仍不变，点击确认后再核对最终值。
5. 用三个可独立重置的测试基准，分别走“用云端”“用本地”“都留（云端另存副本）”。“都留”要现场确认下载已成功，打开副本核对其中保存的是对应云端槽的值，并另外用主账本备份验证当前完整内容。它是冲突模块副本。

**通过标准**：按明确选择收敛，双方再次同步后同一冲突不循环。两个商品变动都属于“商品”槽，同一槽选择一边可能舍弃另一边的修改；用户应能从差异和副本辨认这些内容。较新修改时间与后台同步时间要分别留证。

### SYNC-03 不同模块合并、过期决策和抢写

1. A/B 回到共同基准 R，双端断网。A 新增一件 Papa 商品，B 增一笔 `12.34` 公共支出。A 先连网同步，A 暂不操作。B 连网，若出现云端新增商品提示，选择保留云端商品，再核对其本地收支修改已一起同步。A 再拉取。最终两笔都出现且只出现一次。
2. 重新构造同模块冲突，让 B 保持弹窗打开。此时 A 再提交一个清楚可区分的第三版值。B 用旧弹窗确认“用云端”。预期会重新核对并显示新一轮数据，或明确要求重新操作；不应采纳旧弹窗中已过期的值。
3. 测真正的竞争窗口时，在演练环境用浏览器请求拦截把 A/B 两个带相同 `revision=eq.R` 的 PATCH 暂停在发送前。确认两个请求都已到达拦截点，放行 A 并等待完成，再放行 B。只留请求方法、响应状态及修订号。用云端只读观察记录 R、R+1、以及重新决策后如有的 R+2。
4. 重复一次在 B 执行同步的过程里制造请求失败，随后解除阻断重新同步。检查重试前 B 未保存的修改还在。没有完成写入的请求不能让界面把旧数据当成已同步。跨槽另测一次涉及商品和 Owner 资金的操作，由用例 BIZ-01 的两份记录确认两边没有各采用一半。

**通过标准**：并发提交不出现后到的旧版本直接覆盖先到的成功版本。旧请求若返回空行或被拒绝，最终都应表现为重新比较或明确失败。若流程不能稳定在同一个 R 发出两条请求，该项记“阻塞”，不能以普通手工先后点击替代。

### AUTH-01 匿名、错误账号、旧客户端和移动端

| 身份／操作 | 验收预期 |
|---|---|
| 匿名，主程序及移动页打开 | 不得读取 main 的业务内容或别人的档案。移动端可显示登录提示。 |
| X 登录，测试 main 读取和写入 | UI 与 Supabase 请求均无法获得 O 的 main payload；试写后 O 的业务值和修订号保持不变。权限拒绝或返回空集合都可，能看到或修改数据即失败。 |
| O 登录两设备 | 能读取同一 main，显示同一基准；检查 public 标志保持关闭。 |
| O 用旧版客户端或测试 PATCH，省略修订号 | 服务器拒绝更新；在演练环境再尝试显式改为公开，核对数据库最终仍为私有。 |
| O/X 检查 car 档案 | O 可读自己的一份档案；X 不可读 O 的档案或代插；现有档案不允许普通账号更新或删除。所有写入试探仅针对演练项目。 |
| O 在手机查询，随后退出／会话失效 | 登录后与主程序同一快照，查询、筛选或切换 Owner 不发起对业务数据的写入。真正退出或会话失效后再次打开，不应继续显示先前受保护数据。单纯断网与身份失效分开测。 |

执行细节：

1. 用独立浏览器资料分别以匿名、X 和 O 打开主程序与移动端。在开发者工具只记录业务表请求的路径、方法、状态码和返回行数。刷新会话的认证 POST 可以存在；业务表写请求另计。
2. 试写前后由 O 或演练项目后台读 `id / revision / is_public` 和一条测试字段。后台管理员权限只能用来观察，不能拿来代替匿名或 X。
3. 在线观察时，从现有入口用同一 Owner 对照桌面和手机的库存件数、成本、销售净回款及 Payton 余额各一项，另选一条带 SID 的已售/库存记录检查状态。记录两端数据时间和移动页地址。测试站验证退出和过期时，可以使会话在后台明确失效，确认新请求被拒绝后再观察页面。
4. 同一桌面资料切换云账号前先导出备份。隔离已落盘的本地账本和服务端授权是两件事；如离线本地仍显示旧缓存，应记录是否有清楚提示、是否会误把旧账本发到另一个云账号。

## 3. 完整备份、恢复及失败保护

| 类别 | 应比较的内容 |
|---|---|
| 状态和主业务 | 商品（库存、采购、已售及其他存量状态）、内部 ID、SID、Owner、品相、长短线、购买组、转运、销量/成本、销售渠道、到账标记和入账日期。 |
| 资金及登记 | 公共收支、借贷、Payton 零钱/投资/贷款/互转，财务结算和美淘相关集合、纳税主体名称和税号。 |
| 保留层 | 原备份中已有的每日快照、独立 car 档案。手动备份无操作日志；每日备份可含日志。 |
| 本机层 | 回溯点、授权会话、提醒已读／已报状态、打印或浏览器设置分别记录。只有独立验证到的项目才标记为可恢复。 |

### REC-01 丢失设备后的干净恢复

1. 从源机通过“数据操作 → 导出备份”保存手动文件。另找同日每日备份，并登记自动下载是否实际生成、两份是否带 `operationLogs`。记录业务 11 个同步集合（含纳税主体）、每天快照的日期集合、档案内容和汇总。用回溯恢复测试必须事先备一份完整文件。
2. 新建浏览器资料，断开云配置和登录。用“数据操作 → 导入数据”选择原件的离线副本，确认后截图，刷新，再关闭重开。立即再次导出。真实 11 月 16 日样本的基准为 **1,574 条商品，4 个修复后的 UUID 各存在一次，无内部重复 ID**，并保有旧档案。换用更新样本时重新取基准。
3. 离线全量比较主业务字段。新增当天的聚合快照、程序版本及同步元数据单列；旧快照日期不应无故消失。抽查 UI 的两种 Owner、待确认销售、公共收支、转运、美淘、纳税主体和 car 档案。快照对同日条目的比较用程序的合并口径（日期取并集，同日留生成时间较新的条目）。
4. 用另一独立资料导入每日备份，检查原文件日志仍可离线读取，同时明确登记当前程序导入是否恢复操作日志。5.2.1 的主数据导入路径没有回填原日志，不能据此承诺历史日志可从应用内还原。打开税务提醒核对本机状态是否另需重建。
5. 在演练云端准备已知完整快照。空白新设备先登录 O 再恢复，确认云端旧数据不会被空白本机覆盖。记录账号屡次登录、刷新后与源机一致，核对云端副本只能恢复当前最新快照。若 car 已另行在云端固化，检查首页历史档案入口下载后也能恢复。
6. 反向演练云端误覆盖。先让一份独立浏览器资料保有完整合成账本并断网。在演练云中由另一个同账号设备同步一份刻意少一条商品、少一笔收支的旧版本。保全两份备份后，在持有完整本地账本的浏览器重连，从冲突提示精细选择完整本地数据。最后用一个全新浏览器拉取，逐字段核对云端已恢复为完整版本，采纳过程没有波及其他槽。

### REC-02 导错回退、存储极限、坏文件

1. 断开云同步。以合成账本 A 开始，导入具有明显区别的 B；到“操作日志 → 恢复到最近一次导入前”确认恢复，再导出。必须复核 B 的商品、公共收支和 Payton 测试记录是否已退出主账本，A 的金额及原始记录恢复。快照按合并口径核对，独立 car 档案单列。若使用“数据回溯”按时间恢复，另挑一条购买入库、Payton 资金联动产生的已支持日志，比较恢复到该操作前的商品和账户。遇到无法完整回放的日志，核对是否提示限制并改用完整备份。
2. 按顺序测试取消确认、空文件、截断/破损 JSON、无 `items` 的合法 JSON、商品 ID 无效、car 备份误入主账本入口。每例前后各导出一次，核对无意外覆盖。
3. 在独立资料用浏览器开发者工具以临时数据填到接近当地存储上限，或用自动化对 `ysp_data` 的写入制造 `QuotaExceededError`。分两种故障：回溯点落盘失败，主数据仍可保存；主数据本身也不能保存。第一种验证是否明确提示下载当前备份，点击取消应保留原账本。第二种应明确报错，刷新后仍是旧主数据，演练云端修订号不变。去掉临时配额数据后重新导入，核对能恢复。
4. 另做一个合成且能解析的异常文件，例如重复内部 ID、`items:[]`、关键业务集合缺失。空商品列表可代表合法的空账本，判定重点是误导为完整备份或静默覆盖。若当前校验允许重复 ID 或缺模块文件导入并覆盖，应登记缺陷及丢失的字段或行数。先在文件比较层拦截这类备份，任何生产恢复都停止在导入确认前。

**恢复演练通过标准**：完整备份还原全部应恢复的业务集合。失败不可导致已存账本变化或带坏数据上云。日志、税务提醒、回溯点等另有保留机制或当前限制，报告必须分别列明。
