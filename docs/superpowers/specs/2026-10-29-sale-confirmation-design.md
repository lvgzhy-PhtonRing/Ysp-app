# 销售确认入账与税务导出设计

日期：2026-10-29
状态：待大王陛下审阅批准；本稿仅记录设计，不包含业务代码修改。

## 1. 目标

销售记录继续按下单日服务日常经营统计及闲鱼对账；新增确认入账状态和入账日，用于现金余额校准及按入账日准备税务工作簿。Payton 与 Papa 的未确认交易都进入首页支付宝余额计算器的待确认扣减。

## 2. 方案选择

选择方案一：在现有销售记录上增加确认状态和入账日期，保留当前销售计算和资金更新链路，并由销售状态推导待确认金额。

曾比较的方案二是另建独立财务事件流水。方案二能更完整记录每次资金变动，但会增加数据迁移、回滚和双流水一致性成本；当前需求可由销售记录满足，因此本阶段不采用。

## 3. 确认的业务规则

### 3.1 下单、销售与库存

- 销售发生日仍是买家下单日，继续用于 ysp 销售页面、销售统计和闲鱼“卖出的宝贝”对账。
- 每件售出商品沿用其自身实际采购成本，按个别计价法结转；批量售出也必须逐件保留商品与成本对应关系。
- 本次新增的确认状态不改变商品已售状态，也不改变按下单日展示的销售记录。

### 3.2 待确认与确认入账

- 新登记销售默认未确认。
- 未确认销售的待确认金额按“成交总价 − 平台手续费 − 扣减”计算；快递费已即时记作独立支出，不从待确认金额中扣除。
- 销售页可切换确认状态。打开确认状态时，入账日默认为当天；用户可通过编辑入口调整入账日。
- 确认开关只控制待确认金额是否从支付宝计算器扣减，以及税务工作簿使用的入账日；它不再次改变销售登记时已更新的资金余额。关闭确认状态会清空入账日并恢复待确认扣减，但保留销售、已售库存及运费记录。
- 所有者 Papa、Payton 的未确认销售均计入首页支付宝计算器“未确认交易”；确认后从待确认金额中移除。

### 3.3 资金流与支付宝计算器

销售登记时仍即时更新对应账本。Payton 销售按现有账户规则即时将净回款记入零钱或投资余额，再经 Payton’s 基金计入支付宝计算器；Papa 首页计算器沿用现有“销售利润 + 库存成本转出”的计算逻辑。

待确认金额会在支付宝计算器中扣回尚未实际到账的部分。金额公式为“成交价 − 平台手续费 − 扣减”；正扣减降低待收，负扣减提高待收。快递费不从待确认金额中扣除，因为它已在销售登记时作为支出记入余额。按现有实现，Payton 计入基金的净回款为“成交价 − 快递费 − 平台手续费 − 扣减”；Papa 的销售利润与库存成本转出合并后也得到相同的销售净额。因此销售待收额抵消后，计算器保留快递费的已支出影响。例：Payton 商品成交 100 元，快递费、手续费、扣减均为 0：

| 步骤 | Payton 零钱/投资余额及基金 | 未确认交易扣减 | 支付宝计算器净变化 |
| --- | ---: | ---: | ---: |
| 登记未确认销售 | +100 元 | −100 元 | 0 元 |
| 买家确认，记录入账日 | 仍为 +100 元（确认不再加余额） | 0 元 | +100 元 |

这样销售登记不会提前抬高预计支付宝余额；收到款项并确认后，计算器才反映增加的 100 元。待确认金额按 Papa 与 Payton 合计显示。

### 3.4 费用、补差与回滚

- 平台手续费随入账日归期。
- 用户选择在税务工作簿中将快递费与销售收入一并按入账日归期；系统应明确这是工作簿整理口径，不宣称其必然等同税法计税口径。
- 现有“扣减/特殊扣除”表示买卖双方补差，不代表平台手续费。保留现有字段名并增加说明：“赔给买家填正数；买家补给我填负数”。正数代表卖方资金减少，负数代表卖方资金增加。
- 补差随销售数据即时进入现有净回款/经营计算；待确认金额也纳入补差正负号，使其与即时记账相抵。税务工作簿仅对已确认销售导出，并按入账日将补差作为独立明细列出；利润示例不含补差。
- 整笔回滚代表交易失败或取消：删除销售关系、恢复商品售前库存状态并反向撤销该销售已产生的资金影响，无论此前是否确认。新销售需持久化售前状态和数量，保证刷新、备份及同步后仍可恢复。若取消实际产生快递等费用，用户另在公共支出登记。
- 整笔回滚不同于关闭确认开关：关闭开关只恢复待确认扣减并清空入账日，不改变销售余额、不恢复库存、不删除销售。
- 若回滚发生在已导出的期间之后，系统照常移除销售记录；用户自行处理已申报期间的更正。

### 3.5 历史数据

- 升级前已有销售默认视为已确认，入账日初始化为原销售日期。
- 用户可手动调整少数实际尚未确认的历史记录及其入账日。
- 未确认状态、入账日及必要的迁移标记必须随主数据 JSON、云端同步和导入/导出备份保存；读取旧 JSON 时应兼容缺少新字段的记录。
- 旧版 `calc.unconfirmed` 手工总额迁移为 0。升级前销售默认已确认到账；用户之后可按实际情况逐笔调整确认状态，首页未确认金额由 Papa 与 Payton 的未确认销售自动汇总。

## 4. 税务工作簿规则

- 只导出已确认销售，按入账日归属申报期间；待确认销售不进入该期间销售明细。
- 工作簿不展示下单日期，以免将经营对账日期误当税务期间日期。
- 明细至少分别呈现成交总价、单品实际成本、平台手续费、快递费、补差及参考利润。参考利润示例：售价 100 − 成本 50 − 手续费 1 − 快递费 8 = 41 元；该数值是经营参考，不等于应纳税所得额或税额。
- 补差单独列示并按入账日关联。正数为卖方向买家补款，负数为买家补给卖方。
- 工作簿仍是申报准备和复核材料，不自动判断应税类别、不自动申报或缴税。官方计税规则与本设计的用户选定归期口径需分开提示，申报人应以当前电子税务局和适用政策复核。

## 5. 数据与界面要求

- 销售列表及销售编辑入口能直观看到确认状态、入账日，并能编辑入账日。
- 从库存“卖出”流程登记时，成交弹窗显示醒目的 Owner 标识，并允许选销售渠道；沿用已经确定的销售渠道选项和默认规则。
- 首页支付宝计算器的待确认数字由 Papa 与 Payton 未确认销售自动计算，不再依赖手工录入总额。旧版手工值初始化为 0，并提示用户核对；不得与自动汇总相加。
- 资金明细、操作日志及撤销/重做应能区分销售登记、确认入账、取消确认和整笔回滚，确保每个动作只产生一次对应余额变化。

## 6. 验收标准

1. 新销售默认未确认；未确认期间仍按下单日计入日常销售和库存销量。
2. 100 元成交、0 手续费、0 快递、0 补差的 Payton 未确认销售，使 Payton 零钱/投资余额 +100、基金对计算器贡献 +100、待确认扣减 100，计算器净变化为 0。
3. 确认后默认入账日为当天，待确认扣减减少 100，计算器净变化变为 +100；确认不再次改变 Payton 余额，改入账日期不改变历史经营销售日期。
4. Papa 与 Payton 的未确认销售均进入自动待确认汇总；修改 Owner 过滤或页面视图不得遗漏另一 Owner 的待确认额。
5. 关闭确认只恢复待确认扣减并保留销售及已售状态；整笔回滚才恢复售前库存、移除销售并撤销其全部资金影响。旧记录有日志按日志恢复，无日志时先要求用户确认恢复状态。
6. 正负补差方向、待确认金额计算和工作簿独立明细一致；确认开关不重复改变销售余额。
7. 历史销售迁移后默认确认、入账日等于原销售日；旧版 JSON 可正常读取，新字段可随 JSON/云端往返保存。
8. 工作簿按入账日筛选已确认销售，排除未确认销售，不展示下单日，并保留每件商品成本及各费用明细。

## 7. 实施前仍需在代码审查中核实

- 现有 Payton 销售净额会即时计入零钱或投资余额；实现时确认开关不得重复记账，整笔回滚才反向撤销该流水。
- Papa 当前按“销售利润 + 库存成本转出 − 全局手工未确认金额”计算相关余额；自动化需将旧手工金额初始化为 0，改由销售明细汇总。
- 历史销售回滚：有操作日志时按日志中的售前状态/数量恢复；没有日志时弹窗要求用户确认恢复状态，不猜库存数量。
- 税务导出设计现有字段与新增入账日映射需要在实施计划阶段逐项核对。
