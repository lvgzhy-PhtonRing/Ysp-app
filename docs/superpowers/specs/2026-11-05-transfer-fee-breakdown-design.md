# 转运费拆分设计

## 目标

将新建和编辑转运中的“转运费”拆分为“转运物流”和“海关关税”两部分，保持总转运费等于两项之和，并让后续商品详情中的采购信息展示这两项明细。历史数据不迁移、不重算，继续保持原有成本和总额。

## 现状与边界

- 转运记录目前以 `transfers[].totalRMB` 保存总转运费。
- `submitTransfer` 和编辑转运逻辑使用 `totalRMB` 按商品转运系数分摊到 `purchaseDetails.transferCost`，再更新商品 `cost`。
- 商品搜索器在 `HomeModule.vue` 的“采购信息”中展示采购前成本和单一“转运费”。
- 转运列表只展示总额；本需求只在新建转运和编辑转运菜单中提供两项金额输入。
- 历史转运记录和商品不做批量迁移，也不按新规则重算已有成本。

## 方案

保留 `totalRMB` 作为兼容字段和成本分摊入口，新增两级明细字段：

- 转运记录：`logisticsRMB`、`customsDutyRMB`。
- 商品采购明细：`transferLogisticsCost`、`customsDutyCost`。

新建转运时，表单只接收 `logisticsRMB` 和 `customsDutyRMB`，通过计算值生成 `totalRMB = logisticsRMB + customsDutyRMB`，提交时同时保存三者。编辑转运使用同样的计算规则，并在保存时同步更新关联商品的两项分摊成本及原有 `transferCost`。

按商品转运系数分摊时，分别对两项总额调用现有系数分摊函数：

```text
商品转运物流 = 分摊(转运物流总额, 商品系数, 总系数)
商品海关关税 = 分摊(海关关税总额, 商品系数, 总系数)
商品转运费   = 商品转运物流 + 商品海关关税
商品成本     = 转运前成本 + 商品转运费
```

这样既保留既有消费者对 `transferCost` 的兼容，也保证新增字段与商品成本保持一致。

## 历史数据兼容

- 读取历史转运记录时，如果缺少 `logisticsRMB`，编辑表单将旧 `totalRMB` 放入“转运物流”；如果缺少 `customsDutyRMB`，填 `0`。这样不修改直接保存不会使旧总额变成 `0`。
- 历史商品如果没有两项商品级明细，不回填、不重算；搜索器继续展示原有“转运费”字段。新结构商品额外展示“转运物流”和“海关关税”。
- 所有现有删除、入库、回滚、云端同步、操作日志和报税导出仍以 `totalRMB`/`transferCost` 为兼容基础，避免扩大本次变更范围。

## UI 变化

- 新建转运菜单：将“转运总费用”输入替换为“转运物流”和“海关关税”两个金额输入，并显示自动计算的转运总费用和每系数分摊金额。
- 编辑转运菜单：同样显示两个可编辑金额输入、自动总额和分摊预览；关联已售商品的现有风险提示保留。
- 转运记录列表：继续显示总转运费，不新增可编辑输入。
- 商品搜索器采购信息：对拥有新字段的商品显示“转运物流”和“海关关税”；历史商品保留“转运费”显示。

## 数据流与安全约束

1. 表单提交前将两个输入转换为非负数，统一计算总额。
2. `submitTransfer` 和编辑转运保存记录时同时写入明细与兼容总额。
3. 每次编辑先保存原记录和商品成本快照，再按新总额重新分摊，确保操作日志和回滚信息完整。
4. 明细缺失时只使用历史总额作为编辑表单回退值，不在读取阶段写入数据，避免无意修改历史数据。
5. 商品级两项分摊之和必须等于该商品的 `transferCost`（允许现有金额精度规则带来的最小舍入误差）。

## 测试范围

- 新建转运：两项金额正确生成 `totalRMB`，并分别分摊到商品。
- 编辑转运：修改任一项会更新总额、商品两项分摊、`transferCost`、`cost` 和销售利润。
- 历史兼容：缺少明细字段的旧记录编辑后总额保持不变，旧商品仍能正常展示。
- 商品搜索器：新字段显示两项明细，旧字段仍显示原转运费。
- 现有采购、销售、库存、操作日志和数据保护测试保持通过。
