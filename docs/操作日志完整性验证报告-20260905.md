## 一、验证目标

以「每日快照 + 操作日志」为唯一依据，能完整回溯到任意时间点的数据。本次改造只做两件事：

1. 数据层：补齐每类日志 `detail` 中缺失的回溯必需字段（仅增补字段，不改业务逻辑、不改 message 文案）。
2. 验证层：新增纯函数回溯工具与自动化契约测试，证明日志自身足以支撑逆序还原。

## 二、日志写入位置（单点）

`src/data/store.js:1076` `addOperationLog(type, message, detail)`

- 落盘键：`ysp_ui`（`store.js:181`），经 `saveUiStateToLocalStorage()`（`store.js:1220`）写入 `localStorage`。
- 只存本机，不随云同步、不随每日 JSON 快照导出 —— 详见第五节边界。
- 上限 500 条：`store.js:1120` `length > 500` 时 `splice(500)`。
- 删除聚合：`DELETE_MERGE_WINDOW_MS = 500`（`store.js:16`）、`DELETE_LOG_TYPES = {inventory_delete, purchase_delete}`（`store.js:17`）。同 `sid` 在 500ms 内的连续删除合并为一条日志，`deletedCount` / `deletedNames` / `deletedItemIds` / `deletedItems` 全部累加（`store.js:1096-1101`），**完整商品快照随合并保留**。

`partial` 三类的原因：

- `inventory_unlist` / `purchase_group_edit`：按同 SID 批量联动修改（成本重算、批量改属性），日志记录了变更结果与受影响 itemIds，但未逐件记录每件的完整 before，逆放时无法精确恢复联动重算结果。
- `market_price_update`：只记目标价与联动件数，未记录每件被写入 marketPrices 数组的旧值，且写入是追加而非替换，无法精确逆放。

## 四、回溯模型（reconstructAtTime）

`src/data/logReplay.js` 纯函数，不依赖 store 实例，未接入 UI，仅供验证与研究使用。

```
reconstructAtTime(currentState, logs, targetTime)
  → { state, skipped, barriers }
```

- 取所有 `time > targetTime` 的日志，按时间倒序依次应用逆操作；`targetTime` 为空时回放全部日志。
- 逆操作来源：`deletedItems` / `record` / `loan` 快照直接重插；`changes.before` 逐字段还原；`itemCosts.costBefore` 还原转运前成本；`before.status` / `stock` / `saleDetails` 还原状态。
- 遇到 `barrier`（app_undo / app_redo / app_import / cloud_pull / 云端下载类 cloud_sync）**立即中止**并记入 `barriers`，不猜测。
- 无逆操作器的类型（partial / noop / 未知）记入 `skipped`，继续回放后续日志。
- 输入状态与输出状态互相独立（内部 clone），不污染当前 store。

## 五、已知边界

| 边界 | 说明 |
|---|---|
| 日志上限 500 条 | 超出部分被裁掉（`store.js:1120`）。回溯窗口受限于 500 条，长周期回溯需依赖每日 JSON 快照 + 本窗口日志。 |
| 日志只存本机 | `ysp_ui` 键不随云同步、不随每日快照导出，换设备/清缓存后日志丢失。 |
| 旧日志无法补录 | 本次改造只增补写入字段，已存在的历史日志不含新字段，`getLogBrief` 对这些日志回退显示原 `message`。 |
| 聚合窗口 500ms | 同 SID 连续删除会合并为一条日志；跨窗口则产生多条。回溯依赖 `deletedItems` 累加结果，已随合并保留。 |
| 快照体积权衡 | 每日 JSON 快照仍只存聚合统计指标，不改为逐件快照 —— 单件快照会使快照体积线性膨胀（数百件 × 全字段），与现有体积策略冲突，故保持原状。 |
| undo/redo 是屏障 | 系统撤销/重做直接替换整份状态，日志无法表达其内部变更，回放遇到即中止。 |

## 六、自动化验证结果

`npm test`：**12 个测试文件 / 98 个用例全部通过**。

`operationLogCompleteness.test.js`（9 例）：

1. `full` 能力类型都有契约要求，每条契约项都有能力分级（防止两表漂移）。
2. 业务链路产生的每条日志都满足回溯契约 —— 覆盖采购新增→转运→入库→编辑库存→销售→编辑销售→下架→手动添加→编辑→删除→采购删除→收支增改删→借贷增改删→calc 更新共 20 条日志，逐一 `validateLogDetail` 断言无缺字段。
3. 删除日志保留完整商品快照（含 `purchaseDetails.transferCost` / `saleDetails.price` / `inStockDate`），且快照与 live 对象引用独立（深拷贝）。
4. 同 SID 连续删除合并为一条日志，`deletedCount=2`、`deletedNames` / `deletedItemIds` / `deletedItems` 均累加且契约通过。
5. **回放所有日志可完整还原到操作前状态**（含转运成本、入库状态、销售/下架状态、编辑结果、删除还原，`skipped` 与 `barriers` 均为空）。
6. 回放 `calc_update` 可还原到操作前参数。
7. 遇到状态替换类屏障即中止并记录。
8. 无逆操作类型的日志记入 `skipped` 而不中断回放。
9. `targetTime` 仅回放该时间点之后的日志。

`operationLogDisplay.test.js`（11 例）：类型元数据与未知类型回退、模块标签、逐类型第一层文案模板、无 detail 回退 message、五种区块顺序与消费字段去重、嵌套值压缩为 JSON、旧日志零区块、`hasLogDetail` 判定。
